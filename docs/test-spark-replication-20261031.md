# TEST-архитектура 31.10.2026: Synology + бесплатный Firebase Cloud Firestore (Spark)

## Решение пользователя

Развивать репликацию «Учёта самосвалов» **без Cloud Run, Cloud Functions,
Google Cloud Billing и тарифа Blaze**. Внешний компонент только **Cloud
Firestore** (стандартная база Firebase в проекте `samosval-offline`)
с бесплатным тарифом **Spark**. Файловый Cloud Storage for Firebase
**не является бесплатной заменой Firestore на Spark**: после изменений
2025 года для него требуется Blaze. Поэтому файлы, фотографии и бэкапы
НЕ переносить в Cloud Storage.

Это не означает «без серверов Google вообще»: Firebase Firestore
физически размещается в инфраструктуре Google. Отдельный API, VM, Cloud
Run и Google Cloud Billing в новом проекте не используются.

## Топология

1. Обычный режим: PWA (GitHub Pages) через существующий HTTPS API пишет
   на домашний **Synology DS923+**, PostgreSQL `samosval_test`.
2. На NAS — независимый от телефона процесс из
   `server/src/test-replica-runner.mjs`, который читает упорядоченный
   SQL 014 outbox и доставляет транзакции в **DEFAULT database** проекта
   `samosval-offline` под отдельным namespace
   `samosval_test_replica/v1`. Использует Firebase Admin SDK на NAS
   и защищённые серверные credentials вне GitHub и PWA.
3. Управление владельцем записи находится в
   `samosval_test_replica/write_owner`: один владелец/эпоха, нет
   разрешения двум самостоятельным writers.
4. При подтверждённом переключении браузеры напрямую используют
   **Firebase Auth + Firestore Web SDK**. Никакого HTTP Cloud Run API.
   Действия обрабатываются транзакциями Firestore, с правилами доступа
   и идемпотентными идентификаторами. На текущий момент этот пункт
   **только проектируется**: готов безопасный клиент чтения владельца,
   а бизнес-транзакции браузера ещё НЕ разрешены.
5. После восстановления NAS — сверка журналов и обратная доставка
   операций в PostgreSQL; только потом новый подтверждённый владелец
   записи — Synology.

### Обязательное требование к потере последних рейсов

Асинхронное зеркало **не обеспечивает нулевую потерю** при внезапном
отказе NAS. Поэтому до включения настоящего авто-failover нужно
либо подтверждать критическую операцию только после её безопасной
фиксации в Firestore, либо блокировать повышение резерва при
неразрешённых/неподтверждённых изменениях на NAS. Нельзя по одному
таймауту включить Firebase и притвориться, что копия полная.
Сейчас код относится ко второму, fail-closed варианту.

## Лимиты Spark Standard — вся БД проекта, не отдельный модуль

| Ресурс | Бесплатная квота |
|---|---:|
| Данные | 1 GiB |
| Чтения | 50 000 документов/сутки |
| Записи | 20 000 документов/сутки |
| Удаления | 20 000 документов/сутки |
| Выгрузка | 10 GiB/месяц |

Счётчики объединяют все устройства и приложения проекта.
При исчерпании Spark приложение может потерять доступ к квоте, но
платежа сверх бесплатного плана не появляется; предусмотрены ограничения
по продуктам и периоду. Проверять usage в Firebase Console, а не
выдавать локальные оценки за точные серверные цифры.

Официальные ссылки:
- https://firebase.google.com/pricing
- https://firebase.google.com/docs/firestore/pricing
- https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024

## Что изменено для снижения расходов

- `server/src/test-replica-runner.mjs`: каждые 4 секунды проверяется
  **только локальный PostgreSQL**. Если outbox head и локальная квитанция
  совпадают, к Firestore не обращаться. Для обнаружения рассинхронизации
  выполняется отдельная удалённая контрольная сверка раз в 10 минут.
  Это убирает до ~43 200 пустых Firestore-чтений/сутки.
- `server/src/test-writer-guard.mjs`: экспериментальный server-side
  writer heartbeat теперь 30 сек вместо 8 сек, при неизменном
  60-секундном lease. До ~2 880 owner writes/сутки вместо ~10 800.
  Он включается только `TEST_WRITER_FENCE_ENABLED=1`; при недоступности
  Firestore может останавливать новые NAS-записи — не включать вслепую.
- `server/src/test-spark-limits.mjs`: initial snapshot с числом строк
  более 6 000 отклоняется **до загрузки**. Оценка предполагает не менее
  одного удалённого чтения на строку при верификации и одну удалённую
  запись на строку. Это мягкий ограничитель, а НЕ реальная проверка
  остатка глобальной квоты.
- SQL 014 уже исключает обычные `server_control_state` heartbeat
  изменения из outbox, чтобы не реплицировать метрики каждые секунды.
- Удалённые транзакции сохраняют проверку хеша и квитанции, а
  PostgreSQL получает подтверждённый курсор только после Firebase.

## Текущая готовность / запреты

- Зеркало на NAS: **код и PostgreSQL CI**, не включено в живом
  тестовом NAS, нужны собственный доступ к Firestore и проверенный бэкап.
- `test-app/synology/spark-owner.mjs`: прямое чтение двух документов
  владельца и метаданных через Firebase Web SDK в одной read-only
  транзакции; проверяет project id, generation, digest, epoch, UID,
  и не может само повышать резерв или записывать бизнес-данные.
- `docs/firestore-spark-owner-readonly.fragment.txt`:
  **неопубликованный фрагмент** правил для чтения только этих двух
  документов. Нельзя заменять им действующие Firestore Rules целиком.
  Пока нет реального emulator/live правила и синхронизации ролей,
  нельзя утверждать, что браузер готов для резервных записей.
- Старый Cloud Run deployment workflow удалён из ветки;
  архив исходников создан в
  `backup/failover-cloud-run-before-spark-20261031`.
- Настоящий авто-failover, браузерные записи Firestore,
  полноценная обратная синхронизация всех модулей и полевой тест двух
  телефонов ещё не завершены. `readyForFailover=false` не поднимать
  вручную. Обычная TEST/production страница и NAS не менялись.

## Далее

1. Проверить PostgreSQL + Firestore на изолированном тестовом наборе,
   сервисный credential хранить исключительно на NAS, не в GitHub.
   Проверить существующий Firebase Spark usage прежде чем зеркалировать.
2. Доработать и прогнать в Emulator полный Firestore Security Rules
   (включая запрет spoofing, role revocation, атомарные load/TTN,
   immutable operation IDs, head/epoch). Договориться о бюджете
   direct-client транзакций и размере начального архива.
3. Подключить Firebase Web SDK к той же бизнес-схеме без HTTP-сервера,
   повторяя уже работающий сценарий учёта рейсов в Firebase; обеспечить
   совместимые квитанции для обратного переноса на NAS.
4. Протестировать сбой NAS, отставание реплики, длительную смену,
   повтор ACK, смену владельца и восстановление на двух операторах.
5. Выпустить установочный TEST через проверенный CI и админку,
   ни разу не тронув `index.html` и production.

## Этап 2: изолированный прямой read-only доступ телефона

Следующий выполненный шаг TEST-ветки:

- `server/src/test-spark-access.mjs` формирует отдельную запись
  `samosval_test_replica/v1/access_<generation>/<firebase-uid>` для
  каждого подтверждённого аккаунта PostgreSQL. В ней только собственный
  профиль, статус и разрешения роли, без раскрытия таблицы `app_users`.
- При **первичной** загрузке эти документы создаются, сверяются
  и только затем публикуется указатель поколения метаданных.
- При изменении статуса пользователя и роли обновление access-документа
  выполняется **в той же Firestore-транзакции**, что и доставка
  соответствующих outbox-событий. При удалении пользователя его grant
  удаляется. Если проекция прав опережает последнюю подтверждённую
  последовательность зеркала, телефон обязан отказать в доступе,
  а не показывать смесь двух состояний.
- `test-app/synology/spark-line-reader.mjs` — отдельный
  браузерный read-only адаптер. Он запрашивает состояние владельца до
  и после чтения, проверяет право `line` из собственного access-документа,
  сверяет SHA-256 ID и JSON-форму каждой строки и собирает только
  `line_trucks`, `shifts`, `line_truck_statuses`,
  `line_logs`, `workspaces`. На отдельную таблицу установлен
  предел 300 записей: при превышении возвращается ошибка вместо
  неполной сводки.
- `docs/firestore-spark-line-readonly.fragment.rules` — **черновик**
  правил, разрешающий только ограниченный GET/LIST оператору с доступом
  к линии. Любые клиентские CREATE/UPDATE/DELETE запрещены.
  Действующие Firestore Rules не изменены.
- `.github/workflows/spark-firestore-security.yml` запускает
  **локальный** Firestore Emulator без обращения к живому проекту.
  Проверяет двух разных пользователей, запрет чужих профилей,
  фильтр разрешённых таблиц, отзыв доступа и запрет подмены владельца.

### Главная ещё не решённая часть

Хранимые в зеркале SQL-строки сериализованы в `rowJson`.
**Firestore Security Rules не могут безопасно исполнять всю
серверную PostgreSQL бизнес-логику из JSON-строки.**
Для полностью самостоятельной записи телефона без Cloud Run нужно
отдельное типизированное представление данных линии в Firestore
и тщательная проверка транзакций в Security Rules: границы времени
ходки, `cycleRevision`, владельца/эпохи, uid/роли, idempotent receipt,
погрузки в двух вкладках и неизменяемого аудита. Пока это не готово,
**автопереключение для записей выключено**.

Наличие успешного CI/emulator теста доказывает только код/модель
доступа на синтетических данных. Не доказывает работоспособность
полного NAS → Spark → NAS на живых смартфонах.
