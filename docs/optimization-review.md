# Оптимизация: предварительная оценка задержки событий

Статус: анализ исходников, без изменения алгоритма синхронизации. Наблюдение пользователя: сеть есть, карточка перемещается сразу, затем долго видны «ОФЛАЙН» и красный индикатор, позже подтверждение приходит.

## Что подтверждено кодом

1. Любое действие arrive/load/ttn сначала попадает в локальную очередь. Надпись «ОФЛАЙН» показывается по наличию pending-операции, а не по реальному состоянию сети. Поэтому эта надпись сама по себе не доказывает отсутствие интернета.
2. offlineReplayJournal обрабатывает операции последовательно. До новых pending он ждёт доставки уведомлений и аудита для ранее подтверждённых операций. После каждого подтверждения снова ожидает offlineNotifyAccepted. Эта функция последовательно делает server GET и возможный SET уведомления, затем server GET и возможный SET аудита. Медленный вспомогательный запрос задерживает следующий основной статус.
3. Основная транзакция последовательно читает appConfig, текущую смену, статус машины; для погрузки также существующий лог. Дополнительно действует обёртка журнала истории. Небольшой объём данных не означает малое число сетевых обменов.
4. После ошибки транспорта применяется увеличивающаяся пауза: 4, 8, 16, 32, до 60 секунд. Повтор очереди по интервалу 8 секунд. Это может объяснять длинный красный статус после временного сбоя. До подтверждения основного transaction другие клиенты не увидят новый статус.
5. Включён experimentalForceLongPolling. Это режим совместимости транспорта. Из кода нельзя заключить, что именно он виноват: нужно сравнение сетевых замеров.
6. Подписки получают полные общие коллекции, включая архив. Многие callbacks сериализуют большой state в localStorage и инициируют перерисовку. На слабом телефоне большой архив может добавлять задержку UI, но это не доказывает задержку самого серверного commit.

## Приоритет проверки

Наиболее конкретный кандидат — ожидание вспомогательных уведомлений/аудита перед следующей основной операцией, усиленное ретраями. Отдельная проблема — слово «ОФЛАЙН» для любой неподтверждённой операции. Причину красного состояния в конкретном сеансе без логов назвать доказанной нельзя.

Нужны времена: локальное сохранение → старт транзакции → подтверждение → получение коллегой; отдельно длительность уведомления/аудита, число попыток, коды ошибок, размер очереди. Проверять двумя устройствами при хорошем интернете и после возврата из офлайна. UID, номера машин и сообщения не отправлять в стороннюю телеметрию.

## Предложения, пока НЕ реализованные

- Разделить основной commit и долговечную очередь побочных эффектов, сохранив идемпотентность, авторство и восстановление истории.
- Различать «Сохранено на устройстве / отправляется» и реальную недоступность сервера.
- Перезапускать отправку после подтверждённого восстановления связи, сохранив ограничения повторов.
- Сравнить обычный транспорт и long polling на тех же устройствах.
- После замеров ограничить архивные подписки и частоту тяжёлой сериализации.

Не убирать транзакции, проверки revision, детерминированные идентификаторы рейсов или подтверждение сервером: это вернуло бы риск двойного учёта. Прежде чем обещать ускорение, нужно измерить реальный участок задержки.
