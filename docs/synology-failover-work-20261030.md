# Firebase-резерв TEST: реализация начата 30.10.2026

Запрос: автоматическое переключение Synology → Firebase и принудительный выбор сервера в админке для тестов. Область: TEST samosval-offline / main_workspace. Рабочую версию не менять.

## Реализовано в отдельной ветке

- server/src/failover-policy.mjs: модель единственного владельца записи, монотонная эпоха, аренда NAS 30 секунд, три отдельных сбоя перед автоматическим переходом, проверка контрольной суммы и номера актуальной копии. Принудительные режимы auto / synology / firebase. Возврат на NAS допускается только после сверки текущей копии; автоматический возврат требует 60 секунд устойчивой готовности. Новая запись Firebase сбрасывает ожидание возврата.
- server/src/failover-coordinator.mjs: общий документ Firestore test_failover/main_workspace, транзакционная смена эпохи и проверка прав администратора на каждой повторной попытке. При недоступном координаторе независимый локальный владелец записи не создаётся. Подключение к другому Firebase-проекту запрещено.
- test-app/synology/failover-client.mjs: контроллер команды админки, подтверждение общего для всех операторов режима, защита от двойного нажатия и смены аккаунта, отображение готовности каждой копии. Счётчик сбоев не считает одновременные запросы одного опроса отдельными сбоями; offline, 401/403/409/429 и проблемы авторизации не включают переключение.
- Регрессионные проверки включают два координатора, гонку продления аренды с переходом, одновременную публикацию изменения и ручное переключение, потерянный ответ, устаревшую форму админа, отзыв доступа и запрет возврата к старой копии.

Это ещё не рабочий failover: модули пока не подключены к HTTP/runtime и не изменяют установленный сервер или опубликованную тестовую сборку. Флаги готовности не должны выдаваться без реальной проверки обоих адаптеров и данных. Модульные проверки модели не являются проверкой работающей репликации.

## Совместимость с TEST 4.1.0 и обновлением сервера через админку

- Целевая ветка установки — TEST Synology 4.1.0. В GitHub `releases/nas-test.json` указан именно выпуск API 4.1.0 (отдельно проверять фактическую установленную версию по админке/heartbeat). Резервный Firebase нужно интегрировать поверх этой версии, а не поверх старого API 4.0.1.
- Встроенное обновление серверной части через админку обслуживается `server/src/server-control.mjs`, `server/updater/release.mjs` и `server/updater/agent.mjs`. Обновлятор проверяет коммит, CI, SHA-256 файлов, делает проверенный бэкап и при отказе контейнера возвращает предыдущий образ.
- Автообновлятор принимает только `server/src/*.mjs` из доверенного TEST-манифеста и не меняет зависимости, SQL-схему, настройки сервисов и собственный код `server/updater/*`. Служебный доступ к Firebase, репликация, миграции и возможные изменения агента требуют отдельной безопасной первоначальной настройки до обычного выпуска через админку.
- Установку будущего релиза с резервированием выполнять через существующий процесс TEST admin → check/update, а не параллельным ручным развёртыванием другого контейнера. Не публиковать манифест и не включать кнопку переключения Firebase до полной интеграции, тестирования прав и обоих направлений репликации. Рабочую версию не изменять.
- Правило безопасности дополнено: запись NAS обновляет отметку актуальности только копии NAS. Firebase считается актуальной лишь после отдельного подтверждения точной резервной копии; иначе ручной и автоматический переход на Firebase запрещён.
- Координатор также требует доверенную функцию `verifyReplica(provider, checkpoint)`: проверка неизменяемого снимка Firestore сама по себе не доказывает, что физическая PostgreSQL NAS или действующий Firebase-адаптер применили данные. Проверка выполняется для обеих копий при подготовке, при подтверждении репликации, публикации записи и непосредственно перед ручным/автоматическим переходом и возвратом. При отсутствии функции или отрицательной проверке состояние не переключается. Это только защитный контракт: реальную проверку состояния каждого backend нужно ещё реализовать и испытать; нельзя подменять её постоянным true.

## Обязательные следующие части

1. Получить управляемый доступ к TEST Firebase. Сейчас NAS проверяет Firebase ID-токены по публичным ключам и не имеет настроенного служебного доступа для записи реплики. Сессия Google Console в браузере завершена. Публичные apiKey/projectId не заменяют служебный доступ. Приватные ключи не размещать в Git, localStorage или логах.
2. Постоянная репликация всех доменов и квитанций: линия, текущая/закрытая смена, справочники, табель, архив/корзина, роли/профили/заявки, настройки, игры, аудит и восстановление. Включать резерв только после сопоставления количества записей и хешей.
3. Реальное ограждение каждой записи NAS и Firebase общей эпохой; все старые вкладки и потерянные ответы должны пользоваться теми же ID операций. Локальную очередь не очищать и не переносить слепо между разными scope.
4. Подключить проверенный Firebase-адаптер к каждому экрану. Исправить прежние заглушки core/20-backend-mode.js, подключить контроллер к действующей админке, обновить индикатор фактического сервера. Режим хранится в общей конфигурации, а не localStorage администратора.
5. Обратная синхронизация Firebase → NAS с проверкой полной копии перед сменой эпохи. Готовый health endpoint без проверки данных не даёт права принимать записи.
6. Эмулятор Firestore/Rules, интеграционные PostgreSQL-тесты, два разных оператора, обрыв ответа после записи, перезапуск NAS/PWA, записи в резерве и возврат без дубликатов и потерь, сохранение pending-очередей. Отдельно сверить права и невозможность обхода fencing через старый клиент.
7. Перед публикацией создать свежие резервные копии обеих баз, проверить восстановление, собрать TEST/PWA с новым номером и контрольными суммами. Авто и ручной переход включать только после успешной проверки всех перечисленных частей.

Платные Cloud Functions или новый тариф Firebase этой веткой не подключаются. До выпуска проверенного резервирования текущая TEST Synology продолжает работать без автоматического failover.

## Одноразовая сверка при исходном копировании (добавлено 30.10)

Скрипт `server/scripts/reserve-copy-once.mjs` после неизменяемой загрузки и чтения контрольного снимка из Firestore повторно снимает полный согласованный снимок PostgreSQL. Совпадение SHA-256 нужно **на обеих проверках**: Firebase read-back и повторном чтении NAS. Если во время длительной загрузки изменились рейсы, квитанции или любая из 39 таблиц — операция возвращает `reserve-source-changed-during-copy` и **не сообщает об успешной сверке**. При потере NAS после записи архива также возвращается ошибка. Обрыв может оставить в Firestore целостный, но уже старый архив — он не является активной репликой.

Это защита для **однократного копирования**, а не непрерывная репликация. Флаг `sourceUnchangedAtVerification` подтверждает совпадение только на момент повторного чтения: он не доказывает пригодность Firebase для текущей работы, не включает failover и не заменяет fencing, последовательную передачу изменений и независимую проверку Firebase-адаптера. Компонент `server/scripts` не распространяется штатным обновлятором файлов `server/src`; до выпуска потребуется отдельная безопасная настройка без вмешательства в рабочую версию.
