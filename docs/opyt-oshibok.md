## 12. Урок 23.11.2026 (выпуск 1.8.4): 404 на index-working-test.html валил установку SW — штатные обновления не работали ВООБЩЕ

**Симптом:** у владельца обновления ставились только через чистку кэша; страница восстановления писала «Обновление не выполнено: index-working-test.html 404». Приложение при этом работало (страница грузится network-first), поэтому проблема маскировалась годами.

**Что делать при каждом выпуске working-test:** после пуша Pages обязательно прогонять полную сверку RECORDS (все URL → 200 + SHA совпадает), а не только version.json. ## 16. 27.11.2026: после миграции 025 закрытие смены падало, а «закрытая» смена оставалась `historical`

**Симптом:** после окна миграций 025–029 (схема параллельных смен) закрытие смены в рабочем канале перестало работать: `prepare` отвечал **500**, в логах API `23514 shift canonical payload mismatch`; повторный `finish` — `409 shift-not-prepared`. Смену нельзя было закрыть штатно.
**Причина (два дефекта в одном месте, `server/src/shift-close.mjs`):**
1. На `prepare` писатель ставил `is_active=false`, хотя документ помечал смену `closing:true`. Триггер 025 выводит `is_active = (state IN ('active','closing'))`, то есть закрывающаяся смена обязана занимать линию — отсюда ошибка канонического payload.
2. На `finish` писатель ставил `closedAt` и `closedBy`, но **не писал `closedByUid`**. Триггер 025 выводит `closed` только при наличии доказательства закрытия (`closedAt` + непустой `closedByUid`), иначе строка честно попадает в `historical` — состояние мигрированных legacy-строк без доказательства. Внешне «смена закрыта», а в канонической колонке `state` — `historical`.
**Почему тесты не поймали:** утверждение было слабым — `assert.equal(['active','closing'].includes(row.state), false)` истинно и для `historical`. Слабое отрицание скрыло дефект.
**Сделано:** на `prepare` — `is_active=true` (документ остаётся `closing`), проверка готовности через `shift.closing`; на `finish` — `state:'closed'`, `closedByUid:uid`, как это делает v2-закрытие (`shift-close-v2.mjs`). Тест `server/tests/legacy-close-canonical-db.test.mjs` проверяет точные значения (`state='closing'` после prepare, `state='closed'` + `closedByUid` после finish), невакуумность доказана откатом правки (без неё тест падает с `actual: 'historical'`).
**Что делать:** при переносе записи смены на каноническую схему сверять **все** поля, которые триггер выводит в колонки (`state`, `is_active`, `closed_at`, `closed_by_uid`, `closing_started_at`), и писать доказательства, а не только отображаемые алиасы. В тестах утверждать точное ожидаемое значение, а не «не входит в запрещённый список».

## 17. 27.11.2026: у рабочей версии отдельный API, у тестовой — отдельная пустая база

**Что сделано:** рабочая версия переведена на свой домен API `api-samosval.iluxa.pro` (Caddy → `127.0.0.1:18092`, контейнер `samosval-api-prod`) и на прежнюю боевую базу `samosval_working_test_reserve`; тестовый канал остался на `samosval-test.iluxa.pro` → `127.0.0.1:18091` → новая пустая база `samosval_test_clean`. Обе версии больше не делят данные.
**Почему так, а не «просто переключить клиент»:** клиент рабочей версии жёстко содержит адрес API в `core.js` (`WORKING_TEST_UBUNTU_API_BASE`), поэтому адрес меняется только выпуском нового комплекта (1.7.23, build `d075c52cc59177e6`). Правка была точечной: в `core.js` заменены два вхождения `samosval-test.iluxa.pro` на `api-samosval.iluxa.pro`, остальные 144 файла сборки совпадают байт-в-байт с 1.7.22.
**Ловушки:**
- Порт 80 наружу не доходит, поэтому HTTP-01 для нового домена не проходит: в блоке Caddy нужен TLS-ALPN-01 (`tls { issuer acme }` без `disable_tlsalpn_challenge`).
- Пустую базу нельзя создать «просто `createdb`»: миграции 001–029 содержат guard-ы `current_database() <> 'samosval_test'` (004, 006, 008, 012, 013) и `<> 'samosval_working_test_reserve'` (018). Для новой базы их перенацеливают тем же способом, что и в изолированном стенде (`server/tests/helpers/isolated-db.mjs`), а не отключают проверку.
- После создания пустой базы нужно включить табель: `tabel_policy(workspace_id='main_workspace', enabled=true, import_sha256=<любой стабильный хеш>)`, иначе все обращения к табелю дают `409 tabel-not-ready`.
- Первый зарегистрированный пользователь в пустой базе становится администратором (`bootstrap`); проверочных пользователей после проверки удалять вместе со сбросом `identity_state.initialized=false, owner_uid=NULL`, иначе владелец не станет первым админом.
**Сторож:** `samosval-api-watchdog` расширен — проверяет и поднимает оба контейнера (`samosval-api-prod` на 18092 первым, затем `samosval-api-working-test` на 18091).

**Поправка того же дня (решение владельца):** пустая база для тестового канала оказалась негодной — экраны «Настройки», «Игры», «Вспомогательные данные» и снимок архива читают данные импорта и без них отвечают 409 (`identity-not-ready`, `games-not-ready`, `settings-not-ready`); у владельца тестовая версия «не грузилась». Правильный способ разделения — **полная копия рабочей базы**: `pg_dump -Fc` рабочей базы → `createdb` → `pg_restore`, базы после этого развиваются независимо. Копия проверена: 27 смен, 19 пользователей, 16 архивов, 59 записей табеля — совпадает с рабочей; вход прежним паролем, все маршруты 200. Вывод: «пустая база» годится только для стендов с синтетическими данными, а для рабочей копии канала нужен снимок боевой базы.

**Проверено:** браузер 393×852 на отдельной копии базы (`samosval_test_qa`, чтобы не мусорить в канале): 14 шагов, 0 провалов — вход админом, старт смены, добавление машины 111, прибытие, погрузка без ошибки, рейс добавлен, экран игр открыт и не закрылся за 45 с, автомат открыт и не закрылся за 20 с, второй пользователь (прораб) видит ту же смену, машину и рейс.
