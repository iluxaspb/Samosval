# TEST Spark — прямые транзакции прибытия и погрузки (этап 3)

**Статус: экспериментальное исследование на изолированном Firestore Emulator,
НЕ опубликовано в живой базе и НЕ включено на телефонах.** В production и
на установленном NAS никакие изменения не применялись.

## Почему нельзя разрешить запись в существующее SQL-зеркало

Synology хранит строки PostgreSQL в \`rowJson\` вместе с неизменяемым
журналом SQL 014. Firestore Security Rules не могут исполнить весь код
Node.js бизнес-правил и правильно разобрать произвольные сериализованные
SQL-строки. Разрешение браузеру их редактировать означало бы
возможность обойти ограничения и испортить восстановление.

## Новая типизированная схема

При начальном переносе сервер Synology независимо записывает:

- \`typed_config_<generation>/active\` — серверная активная смена и
  минимум минут между ходками;
- \`typed_trucks_<generation>/<truckId>\` — принадлежность самосвала,
  объём, признак ГАИ;
- \`typed_status_<generation>/<truckId>\` — ревизия цикла, время
  прибытия/последней загрузки, ID последнего действия, состояние линии;
- \`access_<generation>/<firebaseUid>\` — серверные права из
  PostgreSQL, отдельно для каждого пользователя.

Клиенты имеют только чтение этих серверных полей. Когда в NAS
изменяется самосвал, смена или статус, типизированная копия
передаётся в **той же транзакции Firestore**, что и событие
SQL 014 и новый подтверждённый курсор. Если PostgreSQL успел измениться
пока изготавливался снимок, значение \`sourceSequence\` не позволяет
браузеру использовать обгоняющую копию до завершения репликации.

## Прототип браузерной записи

Экспериментальный \`test-app/synology/spark-line-writer.mjs\` выполняет
одну транзакцию Firestore на действие:

- ARRIVE: увеличивает \`cycleRevision\`, устанавливает
  \`arrivedAt=serverTimestamp()\` и создаёт неизменяемую квитанцию
  \`typed_ops_<generation>/<operationId>\`;
- LOAD: дополнительно очищает прибытие, ставит
  \`lastLoadAt=serverTimestamp()\`, создаёт \`typed_logs_<generation>/load_<operationId>\`,
  привязанный к статусу и квитанции;
- при потере ответа попытка с тем же ID должна находить оригинальную
  квитанцию; новая операция не придумывается;
- чтение владельца, прав, смены, машины и её ревизии происходит
  **перед** внесением всех изменений, как того требует Firestore.

Действия ТТН, отмены прибытия и сброса пока намеренно **не принимаются**.
Погрузка из старой локальной очереди также потребует полного тестирования
семантики времени до включения на реальных телефонах.

## Экспериментальные Security Rules — только эмулятор

\`docs/firestore-spark-line-write-experimental.fragment.rules\`
добавляется к локальной тестовой копии старых правил при
\`SPARK_EXPERIMENTAL_WRITES=1\`. Реальные правила Firebase Console
не изменены. В правилах проверяются:

- Google Firebase Auth UID и роль из серверного access-документа;
- совпадение проекта, поколения, эпохи владельца и курсора;
- владелец \`firebase\` и подтверждённое \`readyForFailover=true\`;
- существование активной смены и самосвала на линии;
- переход \`cycleRevision: N → N+1\`;
- запрет погрузки без прибытия и запрет слишком ранней повторной ходки;
- единственная операция/квитанция и журнал нагрузки с привязкой UID,
  данными серверного самосвала и временем \`request.time\`;
- отсутствие возможности подменить системный owner/ACL/meta.

Сценарии CI в \`server/tests/test-spark-write-emulator.cjs\`:
два независимых пользователя одновременно грузят одну карточку;
один единственный подтверждённый журнал; повтор того же operation ID;
отзыв прав; передача владельца; попытки подделать статус, квитанцию
и объём.

**Важно:** успешные тесты эмулятора НЕ равны готовности к выпуску.
Отсутствует обработка всех модулей и согласованный двусторонний
протокол восстановления PostgreSQL. В данной ветке реальные флаги
\`readyForFailover\` остаются выключенными.
