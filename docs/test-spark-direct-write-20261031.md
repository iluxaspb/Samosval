# TEST Spark — прямые операции линии без Cloud Run (31.10.2026)

**Состояние: экспериментальная разработка, PR №71 в черновике.**
Никаких изменений production, установленного NAS, живых Firestore Rules или
кэша телефонов. Биллинг Google Cloud/Blaze не требуется.

## Целевая архитектура

- Synology DS923+ + PostgreSQL — основной сервер и единственный writer
  до подтверждённой передачи эпохи Firestore.
- SQL 014 outbox на NAS доставляет данные на бесплатный Cloud Firestore
  Standard в тестовом проекте `samosval-offline`.
- Firebase Auth и Web SDK телефона напрямую читают владельца из Firestore,
  без HTTP Cloud Run/Firebase Functions и постоянного Google API-сервера.
- При отставании копии, несогласованном владельце или невозможности
  проверки — режим fail-closed: не отправлять запись в две базы.
- Ни одно автоматическое повышение резерва до полной сертификации не
  включено. `readyForFailover` в зеркале остаётся `false`.

## Выполнено в коде

**Типизированное зеркало** `server/src/test-spark-typed.mjs`:
`typed_config_<generation>/active`,
`typed_trucks_<generation>/<truckId>`,
`typed_status_<generation>/<truckId>` и отдельная
`access_<generation>/<uid>` проекция реальных PostgreSQL прав.

**Одна атомарная запись на действие.** В
`test-app/synology/spark-line-writer.mjs` обновляется один статус
самосвала с `cycleRevision`, `ttnRevision` и `reserveHistory`.
`reserveHistory` — **неизменяемая карта** по operation ID, где хранятся:

- тип действия, UID оператора, epoch, серверное время `at`;
- `ordinal` — порядковый номер действия на конкретной машине;
- нормализованный исходный `intent` и SHA-256 его канонической формы;
- данные о погрузке/объёме/ГАИ либо о коллекции ТТН.

Это одна транзакция Firestore без второго сервера и отдельной записи
журнала. При потерянном подтверждении повтор с тем же ID находит
уже сохранённую операцию; подмена содержимого существующей записи
запрещена правилами.

**Поддерживаются ARRIVE, LOAD, TTN.** Отметка ТТН до погрузки
получает статус `pending` и автоматически связывается с новым
подтверждённым рейсом; снятие отметки не изменяет номер ходки.
Сброс, отмена/восстановление журнала, закрытие смен и другие модули
пока не готовы для прямой записи.

**Security Rules:** только
`docs/firestore-spark-line-write-experimental.fragment.rules`, который
компонуется в локальном CI через
`SPARK_EXPERIMENTAL_WRITES=1`. Это **не действующие Rules**.
Проверяет Firebase Auth UID, роль и отзыв прав из NAS, owner/epoch,
поколение, номер ревизии, минимальный интервал погрузки, уникальность
операции в журнале, ТТН, привязку объёма к серверному самосвалу и
невозможность переписать старую историю.

Firestore Rules Emulator ограничивает выражения до 1000 на запрос.
Для прохождения в один документе устранены избыточные повторные
вычисления; полный хеш исходного intent дополнительно независимо
сверяет серверный предохранитель восстановления.

## Добавлено после dry-run: PostgreSQL typed replay (TEST, без handback)

- \`server/sql/015_spark_replay.sql\` создаёт отдельную durable
  \`reserve_spark_replay_checkpoint\` и таблицу
  \`reserve_spark_log_aliases\`. Обе исключены из обычного outbox/зеркала.
  Установка миграции **не включена в опубликованный NAS updater**.
- \`beginSparkTypedRecovery\` при включённом серверном fence требует
  совпадающие подтверждённые NAS/Firebase sequence и SHA-256, \`typedProtocol=1\`,
  \`readyForFailover=true\`, единоличного владельца \`firebase\`, пустых pending
  и отсутствия смешанного legacy \`reserve_ops\`. Атомарно меняет
  epoch/owner на \`reconciling\`, блокируя новые телефонные записи.
- \`startSparkPostgresReplay\` читает frozen manifest и согласованный
  MVCC-снимок PostgreSQL, проверяет всю последовательность существующими
  правилами \`applyLineOperation\` и сохраняет хешированный план в
  контрольную таблицу. При перезапуске использует ранее сохранённый план,
  не сравнивая уже восстановленные карточки с первоначальным снимком.
- \`replaySparkPostgresNext\` применяет **одно подтверждённое событие на
  SQL-транзакцию**: line receipt, статус, журнал, аудит, рейс, alias,
  outbox и контрольная точка фиксируются атомарно. Записи не используют
  часы восстановления вместо проверенного Firebase server timestamp.
  Уведомления о давних действиях повторно не отправляются.
- Перед следующим событием проверяется неизменность PostgreSQL outbox
  с прошлого шага и владелец Firebase в frozen-поколении (только два Firestore-документа,
  без дорогостоящего повторного обхода коллекций). Полный исходный
  журнал снова сверяется при завершении replay. Два recovery
  worker сериализуются блокировкой checkpoint; при SQL ROLLBACK не
  продвигается ни журнал, ни курсор. Потерянный ответ после COMMIT
  устраняется устойчивым \`applied_count\` без повторного начисления рейса.
- Даже когда курсор получает \`state=applied\`, **переход ownership обратно
  на NAS отсутствует**. Старый \`stageRecoveredGeneration\` по-прежнему
  блокирует поколения \`typedProtocol=1\`. Нельзя считать TEST релиз
  годным к установке.

**Контрольные интеграционные тесты**:
\`server/tests/test-spark-pg-replay.test.mjs\` создаёт отдельную временную
базу PostgreSQL 16 с миграциями 001–015, моделирует frozen Firestore,
проверяет ARRIVE → TTN → LOAD, ровно одну квитанцию на ID, историю и аудит,
соответствие резервного и локального ID рейса, атомарный откат при
ошибке SQL, двух параллельных исполнителей и запрет посторонних
изменений в PostgreSQL. Нужен успешный итоговый прогон CI для подтверждения.

## Новый TEST-этап: typed handback после SQL replay (без автоматического запуска)

Добавлен изолированный модуль `server/src/test-spark-handback.mjs` — он **не подключён**
к HTTP API, updater, фоновой репликации и телефонам.

- `stageSparkTypedHandback` допускается только после `state=applied` в
  durable SQL 015 checkpoint. Повторно сверяет исходный frozen
  Firestore manifest, все SQL operation receipts и алиасы рейсов.
- PostgreSQL собирает полный согласованный снимок; новая **детерминированная**
  generation содержит SQL row mirror, typed LINE config/trucks/statuses,
  UID-scoped ACL. При новой generation история `reserveHistory` очищена:
  прежние операции уже атомарно восстановлены в PostgreSQL.
- Все документы загружаются в скрытую generation небольшими пакетами
  с предварительным ограничением бесплатных Spark-записей и полностью
  считываются обратно; несовпадение документов или числа записей блокирует
  публикацию. Одной транзакцией меняются metadata и owner на `handoff`,
  **не** на `synology`. `readyForFailover=false` сохраняется.
- На момент транзакции публикации/возврата владельца удерживается SQL
  `reserve_outbox_cursor FOR UPDATE`: параллельная запись PostgreSQL не
  может незаметно пройти между проверкой снимка и сменой владельца.
- `completeSparkTypedHandback` сверяет SQL checkpoint, неизменность
  outbox, snapshot SHA-256, ACL и typed документы. Только после сверки
  записывает SQL receipt нового snapshot и переводит owner в
  `synology/nas_handoff_pending`; новый NAS worker обязан забрать
  отдельную эпоху через `claimNasOwnership`.
- Повторный запуск после потерянного Firestore ACK не создаёт новую
  generation. Повторение после потерянного SQL receipt ACK разрешено;
  подмена документов, незавершённый SQL replay и посторонний NAS write
  запрещают handback. Механизм намеренно остаётся TEST-only.

Интеграционные проверки добавлены в
`server/tests/test-spark-pg-replay.test.mjs` (PostgreSQL 16 и
изолированные временные БД). Действующий Synology и production не менялись.

## TEST PWA: прямой маршрутизатор Synology ↔ Firestore Spark (изолирован)

В черновой ветке теперь есть:
- `test-app/synology/spark-typed-line-reader.mjs` — по подтверждённой
  эпохе Firebase Auth/Firestore сопоставляет исходный SQL line snapshot
  с типизированными `typed_status` и `reserveHistory`. Подтверждённые
  резервные погрузки появляются в карточках и журнале без второго HTTP-сервера.
  Данные читаются только с сервера, сверяются поколение и исходная
  ревизия, результаты не используются при изменении владельца.
- `test-app/synology/spark-auto-line-client.mjs` — TEST router.
  `synology` вызывает исходный NAS API; `firebase` использует
  Web SDK `spark-line-writer` с транзакционными ARRIVE/LOAD/ТТН.
  `handoff/reconciling` или неверифицированный owner запрещают
  запись в любую базу. Успех NAS-запроса или таймаут **не** повышают
  Firebase до владельца.
- `test-app/source/core/21-nas-runtime.js` подключает эти адаптеры
  **только** при отдельном `<meta name="test-data-provider" content="synology-auto-candidate">`.
  Обычный `index-test.html` и рабочее приложение не содержат
  этого тега. Локальная настройка режима также не активирует маршрутизатор.
- В резерве кроме «Линии» остальные вкладки и SQL-команды недоступны.
  SQL 015 replay также хранит исходный SHA-256 intent. Повторная
  отправка **точно того же** ID, UID и исходного содержимого на NAS
  после handback получает подтверждение старой операции без нового рейса;
  изменённый запрос отвергается как повторное использование ID.
  В обычном PostgreSQL без SQL 015 это исключение выключено.
  Офлайн-журнал сохраняет исходный ID при неопределённом ответе:
  результат Firestore подтверждается локально только после чтения
  typed snapshot с тем же immutable operation ID.
- При Firebase-owner подписка на `write_owner`, метаданные,
  собственную ACL и точечные typed-status документы заменяет частый
  опрос коллекций; при уведомлении об одной машине проверяются
  её конкретный статус, права UID и эпоха владельца, а не все
  карточки сразу. Неподвижная SQL-копия кэшируется только в пределах
  подтверждённого поколения. Редкий heartbeat заново проверяет
  все статусы для обнаружения пропущенных событий.
  Это экономит Spark reads, **но расход проекта пока не измерен
  на двух устройствах**.
- Тестовые файлы `server/tests/test-spark-auto-line-client.test.mjs`
  и `test-spark-typed-line-reader.test.mjs` проверяют запрещённую
  автоматическую промоцию, смену эпохи, повторную доставку, доступ
  после смены учётной записи, защиту от подмены и реактивность.

**Не путать авто-маршрутизацию с авто-промоцией владельца.** Когда
Synology не отвечает, а Firestore owner ещё `synology`, клиент
останется с локальной очередью до подтверждённого серверного
переключения. Для настоящей бесшовной работы необходимо развернуть
проверяемый NAS fencing, безопасную промоцию на Firestore и
испытать полный цикл на реальных TEST серверах.

**Публикация TEST 4.1.2 пока запрещена:** перенос SQL 015 в updater,
боевые тестовые Rules Spark, два реальных оператора, два телефона,
сбой/восстановление NAS и расширение поддерживаемых модулей не завершены.
Вся новая логика доступна только в исходниках DRAFT PR №71.

   на восстановленной из бэкапа TEST базе NAS.** Не включать механизм
   автоматически, пока не готов контролируемый upgrade SQL 015.

   провести управляемое реальное переключение, исключить split brain
   и предусмотреть несколько последовательных циклов failover.
3. Подключить test-only Spark Web SDK router в PWA с реактивными
   слушателями без расходования 50 тысяч бесплатных чтений в сутки
   на частые опросы.
4. Реализовать ТТН/журнал/табель/архив/смены/игры/доступ в
   резервном режиме без скрытых записей на старый NAS.
5. Проверить живой Firestore Spark, реальные Security Rules на
   тестовом Firebase проекте и полный цикл на двух реальных устройствах
   с изолированными тестовыми данными.
6. После CI и резервной копии — публиковать TEST, а установку
   NAS через админку выполняет владелец. Production не менять.

**Нельзя объявлять готовым тестовый релиз или включать флаги failover,
пока все пункты безопасности не выполнены.**
