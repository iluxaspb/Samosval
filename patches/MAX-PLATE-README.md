# Госномер картинкой в MAX — добавляемый патч v1

`max-plate-notifications-v1.js` — самостоятельный патч типа **«Заменить функцию»** для исходного `index.html`. Он также добавлен отдельным блоком перед `</body>` оригинального файла. Изменения табеля из ветки 3.2 сюда не перенесены.

## Что изменено

- Для уведомления о машине создаётся PNG 600 × 144: белое поле, тёмная рамка, разный размер букв/цифр, отдельный регион, RUS и флаг — как у карточек приложения.
- Номер фиксируется при постановке уведомления в существующую очередь. Переименование машины до отправки не подменяет номер в старом сообщении.
- Приём на линию, снятие, прибытие, погрузка и ТТН используют прежние триггеры/задержки. PNG добавляется к одному сообщению с прежним текстом. Старт смены без номера и PDF проходят прежним маршрутом.
- В «Админ → Настройки приложения → Уведомления в Max» добавлены **«Посмотреть пример»** и **«Проверить поддержку»**. Пример не отправляет сообщений.
- Повторное применение патча не создаёт повторных обёрток. Обёртка восстанавливается после загрузки других патчей, включая существующий патч ретраев MAX.

## Важная зависимость — сервер отправки

В оригинальном приложении POST идёт на `appConfig.maxUrl`, а не непосредственно в API MAX. Известный клиентский контракт сервера — текст или `document.content_base64`. Исходный код этого сервера не предоставлен. Поэтому поддержка **изображений**, а не файлов, на действующем сервере пока не подтверждена.

Патч запрашивает GET по тому же URL. Только ответ

```json
{"contract":"samosval-max-plate-v1","capabilities":{"image_png":true}}
```

разрешает отправку PNG. Пока такого ответа нет, используется исходный `sendMaxOnce` и текстовые уведомления продолжают работать. Нельзя считать клиентский патч завершённой серверной интеграцией или подтверждённой доставкой картинки в MAX.

Сервер получает **один** POST:

```json
{
  "contract": "samosval-max-plate-v1",
  "request_id": "q_существующий_идентификатор_очереди",
  "chat_id": "существующий ID",
  "text": "прежний текст уведомления",
  "image": {"filename":"gosnomer-123-178.png","mime_type":"image/png","content_base64":"..."}
}
```

Авторизация клиента остаётся прежней. Токен MAX-бота не добавляется в патч. Сервер должен загрузить PNG через `POST /uploads?type=image`, отправить `POST /messages` с `attachments:[{type:"image",payload:{token}}]` и подтвердить результат:

```json
{"contract":"samosval-max-plate-v1","success":true,"message_id":"фактический mid MAX"}
```

После попытки POST патч не досылает отдельный текст «на всякий случай»: сетевой сбой мог произойти после принятия изображения. Повтор идёт через прежнюю очередь с тем же `request_id`.

## Подготовленный серверный адаптер

`server/max-plate-support.cjs` — модуль для Node 20+, без зависимостей и без собственного HTTP-сервера. Он загружает PNG в MAX, повторяет только явно неготовое вложение, переиспользует токен изображения, объединяет одновременные одинаковые запросы и сохраняет квитанцию результата.

Пример подключения к **существующим авторизованным** маршрутам Express (имена маршрута/проверки доступа заменить именами из реального сервера):

```js
const { CONTRACT, createMaxPlateSupport } = require('./max-plate-support.cjs');
const plate = createMaxPlateSupport({
  botToken: process.env.MAX_BOT_TOKEN,
  receiptStore: existingPersistentReceipts // async get(key), set(key,value)
});

// Existing authentication and allowed-chat checks MUST stay in place.
app.get('/send', requireExistingAuth, (req, res) => res.json(plate.capabilities));
app.post('/send', requireExistingAuth, requireAllowedChat, async (req, res, next) => {
  if (req.body?.contract !== CONTRACT) return next(); // Original text/PDF handler follows.
  try { res.json(await plate.send(req.body)); }
  catch (error) { res.status(error.status || 503).json({success:false,error:error.message}); }
});
```

JSON middleware должен пропускать тело до 100 КБ. CORS должен разрешать GET/POST и существующий Authorization для адреса приложения. Нельзя выносить эту ветку перед авторизацией или заменять ей старую отправку PDF/текста.

Для реального сервера нужен долговечный `receiptStore` (ключ включает чат и request_id). Встроенное хранилище в памяти ограничено 1000 записями/24 часами и помогает только в одном процессе, до перезапуска. Даже долговечная квитанция не гарантирует exactly-once, если соединение с MAX оборвалось после принятия сообщения, до получения `mid`: у API нет подтверждённого в этой интеграции ключа идемпотентности. Не обещать отсутствие сетевых дублей сверх возможностей исходной очереди/API.

Адаптер не развёрнут и не подключён к пользовательскому серверу: сначала нужен его код/репозиторий. Реальные сообщения и токены для разработки/тестов не использовались.

Официальная документация: https://dev.max.ru/docs-api/use-cases/sending-messages/media и https://dev.max.ru/docs-api/methods/POST/messages (проверено 24.10.2026).

## Ручное добавление и откат

Если оригинальный HTML уже обновлён, добавлять патч повторно не требуется. Для отдельной старой копии: Админ → Патчи → Новый → тип «Заменить функцию» → вставить **весь** `max-plate-notifications-v1.js` → сохранить. Это IIFE, отдельное имя функции не вводится.

Удаление добавленного блока `MAX PLATE PNG PATCH` из HTML возвращает прежнюю отправку. Если патч установлен через список патчей — выключить его и перезагрузить страницу. Никакие записи базы/правила не изменяются.

## Проверки

```sh
NODE_PATH=/path/to/jsdom/node_modules node tests/max-plate/client.cjs
node tests/max-plate/server.cjs
node tests/max-plate/static.cjs
```

Проверяется протокол с имитацией сети, защита от двойного пути «картинка + отдельный текст», совместимость PDF, сохранение номера, повторное применение патчей, ответ неподготовленного сервера, upload/attachment API и синтаксис исходного HTML. Отдельно проверяется предпросмотр PNG в браузере. Это не проверка реальной доставки в чат MAX.
