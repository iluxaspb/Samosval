# Защищённые участки: предложения НЕ применены

Работа по этим участкам остановлена по явному запрету владельца в ТЗ §0.5 и текущем поручении. Остальные изменения находятся в разрешённых файлах табеля. Здесь нет запроса на изменение production.

## 1. Тестовая PWA и воспроизводимая сборка

Текущий `sw-test.js` хранит контрольные суммы прежних двух файлов табеля и разрешает кэшировать только перечисленные ресурсы. Новый редактор в список не входит. Без обновления новый установленный клиент не получит целостный офлайн-пакет; старый кэш может продолжать показывать прежний табель.

Минимальный исходный diff: [test-builder-NOT-APPLIED.patch](proposals/test-builder-NOT-APPLIED.patch), **4 добавленные строки** в `tools/build-test.py`: включить исходники табеля в hash сборки и runtime-файлы модуля в список ресурсов; убрать дубли URL. Основная логика, shell, порядок модулей и production не меняются.

После одобрения сборщик должен штатно пересоздать `index-test.html` (пути build), `sw-test.js`, `test-app/build-manifest.json` и новый каталог `test-app/build/<hash>/`. Старые каталоги оставляются для открытых клиентов. Для точного просмотра изменения списка кэша подготовлен [pwa-cache-NOT-APPLIED.patch](proposals/pwa-cache-NOT-APPLIED.patch); его контрольные суммы относятся к текущему исходному состоянию и не следует применять отдельно вместо штатной сборки.

Кандидатные байты проверены в памяти тестом `tests/tabel/proposed-pwa.cjs`: целостная установка, открытие всех ресурсов офлайн, отказ при частичном/повреждённом обновлении, нетронутые production/API/запросы записи. Сам действующий PWA-тест текущих защищённых файлов **не проходит**: `Release mismatch ... timesheet-core.js`. Это не замаскировано как успех.

Риски: изменение тестового механизма обновления; требуется полная пересборка, атомарная публикация пакета и проверка на установленной PWA. Альтернатива без доступа к защищённым файлам — исходники в draft PR и локальная QA-страница; это текущий результат.

## 2. Правила новых коллекций и объектные права

Защищённый файл: `firestore-timesheet-test.rules`. Его действующий код и опубликованные правила Firebase не менялись. Старые rules разрешают общий admin fallback для неизвестных коллекций, но не знают новые типы в квитанциях табеля. Поэтому нельзя считать запись новых документов и объектную ACL внедрёнными в реальную базу.

Точный проект diff: [firebase-integration-NOT-APPLIED.patch](proposals/firebase-integration-NOT-APPLIED.patch). Полный **эмуляторный** кандидат: [firestore.integrated-emulator.rules](proposals/firestore.integrated-emulator.rules). Он:

- исключает четыре новые коллекции из широкого fallback;
- добавляет их в проверяемые квитанции;
- проверяет активный аккаунт, главное право табеля, объектную ACL, revision и атомарную квитанцию;
- сохраняет прежнюю валидацию существующих записей;
- вводит объектные ограничения для записей смены/материалов только после появления настроек этого объекта; старые объекты сохраняют старую политику;
- не меняет правила «Линии», рейсов, монет, пользователей, production или иных коллекций.

Оба кандидата — изолированный `firestore.sandbox.rules` и интегрированный — проверяются только локальным Firestore Emulator. Название sandbox не означает, что файл можно публиковать целиком: он намеренно запрещает коллекции основного приложения.

Риски: реальная опубликованная конфигурация может быть новее файла репозитория; серверную ACL нельзя усилить одним добавлением разрешающего `match`, потому что разрешения Firestore объединяются через OR. Перед будущей публикацией требуется сверка с актуальными тестовыми правилами. Даже после разрешения на исходный diff публикация в production в него не входит.

## 3. Исторические сведения «Линии»

Изменения защищённых файлов для нового отчёта не потребовались: используется только чтение существующего журнала по дню. Для утратившихся/неоднозначных старых событий точный состав не выдумывается. Это ограничение исходных данных, а не выполненная миграция или разрешение менять «Линию».

## 4. Защита GitHub — рекомендации, без административных изменений

Защитить рабочую ветку правилами GitHub: запрет прямого push/force-push, PR и обязательное одобрение владельца, обязательные проверки. Для защищённых путей — CODEOWNERS владельца **вместе с правилом обязательного owner review**. Сам по себе файл CODEOWNERS ничего не блокирует. Агенту желательно выдавать доступ только к тестовым веткам через отдельный токен/политику; обычные repository permissions не дают ограничения редактирования по путям.

`.github/**`, CODEOWNERS, repository settings, CI, scopes токенов и настройки веток этот PR не меняет. Скрипт `tests/tabel/guard.py` — локальная проверка границ, а не заявление об установленной серверной защите GitHub.
